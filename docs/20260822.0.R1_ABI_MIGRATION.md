# STN-LABZ ABI 1.4 Agent Migration and Hotload Report

**System Scope:** STN-LABZ Autonomous Agents  
**Migration Target:** STN-LABZ ABI 1.4  
**Reference Platform:** Windows x64  
**Reference Implementation:** ISO C / Windows DLL modules  
**Migration Validation:** PASS  
**Hotload Validation:** PASS  
**Date:** 20260822  

---

## 1. Purpose

This report documents migration of STN-LABZ autonomous-agent module systems from agent-specific module lifecycle interfaces to the common STN-LABZ ABI 1.4 and documents live module discovery and hot replacement established on that architecture.

The report is intentionally agent-neutral.

Individual agents retain their own mission, Core behavior, module capabilities, artifact naming, platform integration, and operational authority. The STN-LABZ ABI provides the common module lifecycle boundary.

Digit was used as the first implementation and runtime-validation environment. Digit-specific results in this report are implementation evidence, not limitations on the scope of the architecture.

---

## 2. Migration Objective

The migration objective is to replace duplicated agent-specific module lifecycle contracts with the established STN-LABZ ABI 1.4 contract while preserving agent-specific behavior.

The intended architecture is:

```text
Agent Core
    |
    +-- STN-LABZ ABI 1.4
    |       |
    |       +-- discovery
    |       +-- verification
    |       +-- qualification
    |       +-- activation authorization
    |       +-- activation
    |       +-- stop
    |       +-- unregister
    |       +-- replacement lifecycle
    |
    +-- agent-specific Core behavior
    +-- module-directory monitoring
    +-- safe module-use coordination
    +-- host/platform integration

Modules
    |
    +-- consume STN-LABZ ABI module contract
    +-- retain module-specific service APIs
    +-- provide qualification and negative validation
```

The ABI defines the lifecycle relationship. It does not replace the internal or agent-specific capability of a module.

---

## 3. Engineering Principle

The migration follows the STN-LABZ engineering principle:

> Stay small, deterministic, and easy to operate.

The migration does not require redesigning working module capabilities merely to adopt the common lifecycle.

The contract between Core and modules changes where lifecycle behavior has become common infrastructure. Agent-specific and module-specific behavior remains at its proper boundary.

Hotload follows the same principle. Filesystem arrival is a deployment trigger; it does not create a second lifecycle system. The owning agent Core detects the event and uses ABI 1.4 for the controlled lifecycle transitions.

---

## 4. Previous Architecture

Before migration, an agent may contain agent-specific names, structures, result types, descriptors, lifecycle functions, or registry behavior that duplicate common module lifecycle functions.

The Digit reference implementation previously included examples such as:

```text
digit_module_result_t
digit_module_host_t
digit_module_descriptor_t
digit_module_qualification_result_t
digit_module_get_descriptor
DIGIT_MODULE_API_MAJOR
DIGIT_MODULE_API_MINOR
```

Those functions were no longer inherently specific to Digit.

The same architectural test applies to another agent: if an interface describes generic module discovery, verification, qualification, authorization, activation, stop, unregister, or replacement rather than the agent's mission-specific behavior, it belongs at the common ABI boundary rather than in another agent-specific ABI copy.

---

## 5. Current Common Architecture

Agents migrated to ABI 1.4 use the common STN-LABZ module contract.

Representative lifecycle interfaces include:

```text
stnlabz_module_result_t
stnlabz_module_host_t
stnlabz_module_descriptor_t
stnlabz_module_qualification_result_t
stnlabz_module_get_descriptor
STNLABZ_MODULE_API_MAJOR
STNLABZ_MODULE_API_MINOR
```

The standard module descriptor export is:

```c
__declspec(dllexport)
const stnlabz_module_descriptor_t *
stnlabz_module_get_descriptor(void);
```

An ABI 1.4 loader expects the ABI-defined entry point.

A module that does not expose the required entry point is rejected rather than treated as compatible.

---

## 6. Ownership Boundaries

A critical migration distinction is the difference between an **ABI consumer** and the **ABI host implementation**.

The owning Agent Core executes and governs the host-side ABI lifecycle.

Module DLLs consume the ABI contract.

```text
Agent Core
    |
    +-- owns host-side ABI lifecycle integration
    +-- owns agent authority
    +-- owns module location and monitoring
    +-- owns safe use/quiescence coordination
    +-- owns deployment triggering and reporting
    +-- owns host/platform services

Module DLL
    |
    +-- includes the ABI module contract
    +-- provides its descriptor
    +-- provides lifecycle callbacks
    +-- provides qualification evidence
    +-- exports stnlabz_module_get_descriptor()
    +-- retains its defined capability
```

A module DLL does not independently embed the Core-side ABI registry implementation.

During the Digit migration, `abi.c` was temporarily compiled into the SQLite module. The resulting unresolved references included:

```text
stnlabz_module_registry_init
stnlabz_module_registry_discover
stnlabz_module_registry_verify
stnlabz_module_registry_qualify
stnlabz_module_registry_authorize_activation
stnlabz_module_registry_activate
stnlabz_module_registry_stop
stnlabz_module_registry_unregister
stnlabz_module_registry_fail
stnlabz_module_registry_find
stnlabz_module_state_string
stnlabz_module_result_string
```

The correct resolution was to remove the Core-side implementation from the module DLL project rather than recursively copying more host implementation into the module.

### Rule

**Modules consume the ABI contract. The owning Core owns the host-side lifecycle integration and authority.**

---

## 7. Module-Specific APIs Remain Module-Specific

Migration does not require every module export to become an STN-LABZ ABI function.

The common boundary remains:

```text
STN-LABZ ABI
    |
    +-- generic module lifecycle

Module-specific API
    |
    +-- module capability
```

A knowledge query, communications operation, context-recognition operation, telemetry service, mission-planning function, or other module capability does not become part of the common ABI merely because the DLL participates in the ABI lifecycle.

This keeps the ABI small and prevents agent-specific functionality from leaking into common infrastructure.

---

## 8. Qualification Preservation

ABI migration does not remove the module qualification gate.

Each module continues through Core-controlled lifecycle processing:

```text
DISCOVERY
    |
VERIFICATION
    |
QUALIFICATION
    |
NEGATIVE VALIDATION
    |
ACTIVATION AUTHORIZATION
    |
ACTIVATION
    |
ACTIVE
```

A successful build is not qualification.

A previous revision's qualification is not inherited by a changed module.

The specific candidate being introduced must satisfy the applicable qualification and negative-validation requirements before activation.

---

## 9. Fail-Closed Loader Validation

During the Digit reference migration, modules still exposing the previous descriptor entry point were rejected:

```text
[MODULE] REJECTED: context_recognition (LOADER_EXPORT_MISSING)
[MODULE] REJECTED: sqlite (LOADER_EXPORT_MISSING)
```

After migration to the ABI-defined descriptor export, both DLLs loaded successfully.

This established the intended fail-closed behavior: an incompatible module contract is rejected rather than silently accepted.

For another agent, equivalent incompatibility must likewise be treated as a failed candidate, not as permission to invent compatibility behavior.

## 10. ABI Version Identification

An agent may report the ABI version against which its running build was compiled.

The Digit reference implementation reports:

```text
STN-LABZ Digit

```

The value is derived from the ABI version definitions rather than maintained as an unrelated agent-specific version string.

Equivalent startup identification is useful operational evidence for other agents adopting the common ABI.

## 11. Hotload Objective

ABI 1.4 migration enables a common live module-management model in which module maintenance does not inherently require shutting down the autonomous agent.

The objective is:

```text
running agent
    |
module directory monitored
    |
new or updated artifact detected
    |
candidate evaluated
    |
ABI lifecycle applied
    |
module becomes ACTIVE
    |
agent remains running
```

The agent does not require an operator reload command to trigger ordinary hotload processing.

The arrival of a valid deployment artifact in the monitored module tree is the trigger.

---

## 12. Module Directory Watcher

The Agent Core watches its module directory while the agent is operational.

The watcher is a host mechanism, not a replacement for ABI lifecycle authority.

Its responsibilities are limited to detecting relevant filesystem changes and initiating the appropriate controlled module path.

Conceptually:

```text
Module directory
      |
      +-- existing module update detected
      |        |
      |        +-- hot replacement path
      |
      +-- previously unknown module detected
               |
               +-- new-module qualification path
```

The watcher does not independently declare a module trusted, qualified, authorized, or active.

Those decisions remain governed by the established lifecycle.

---

## 13. New Module Hotload

When a previously unknown module appears while an agent is running, the agent may process it without restarting Core.

The required behavior is:

```text
NEW MODULE ARTIFACT
        |
        v
filesystem event detected
        |
        v
module identity/configuration validated
        |
        v
DLL loaded as candidate
        |
        v
descriptor validated
        |
        v
DISCOVERED
        |
        v
VERIFIED
        |
        v
QUALIFIED
        |
        v
mandatory negative validation PASS
        |
        v
activation authorized
        |
        v
ACTIVE
```

Failure at a required stage prevents activation.

The existence of a DLL in the module directory is not authority to activate it.

## 14. Existing Module Hot Replacement

An update to an already ACTIVE module uses a controlled replacement path.

The candidate is evaluated before the active revision is disturbed.

```text
ACTIVE revision
      |
      |     versioned candidate arrives
      |              |
      |              v
      |       candidate preflight
      |              |
      |         PASS required
      |              |
      +--------------+
                     |
                     v
             gate new module calls
                     |
                     v
             drain existing calls
                     |
                     v
                 quiescent
                     |
                     v
                  STOPPED
                     |
                     v
               UNREGISTERED
                     |
                     v
               old DLL unload
                     |
                     v
            replacement installed
                     |
                     v
                 DLL load
                     |
                     v
                verification
                     |
                     v
               qualification
                     |
                     v
            negative validation
                     |
                     v
          activation authorization
                     |
                     v
                  ACTIVE
```

This is hot replacement: the affected module crosses a controlled quiescent boundary while the agent itself remains operational.

---

## 15. Candidate Preflight

Preflight protects the currently ACTIVE revision from an obviously invalid replacement.

Before disturbing the active module, the candidate must demonstrate the required compatibility and qualification evidence.

Preflight includes the applicable checks for:

- loadability;
- required ABI descriptor export;
- module identity;
- declared version;
- ABI compatibility;
- verification;
- qualification;
- mandatory negative validation.

A failed preflight is rejected before the active module is stopped.

### Rule

**Do not sacrifice a working ACTIVE module merely because a newer file appeared.**

Filesystem arrival creates a candidate, not authority.

---

## 16. Safe Module-Use Coordination

Hot replacement introduces a runtime condition that ordinary startup loading does not: Core or another approved caller may currently be executing module code when an update arrives.

An active DLL cannot be safely unloaded while execution remains inside that module.

The Agent Core therefore owns safe module-use coordination around callable module exports.

When replacement begins:

```text
replacement pending
        |
        +-- block new calls into affected module
        |
        +-- allow existing calls to complete
        |
        +-- count reaches zero
        |
        v
     QUIESCENT
```

Only after quiescence may the replacement lifecycle proceed to stop, unregister, and unload.

This boundary allows the agent to remain operational under load without unloading code that is still executing.

---

## 17. Operational Continuity Under Load

The hotload architecture does not require the entire agent to become idle.

Only the affected module must reach its safe replacement boundary.

Other Core functions and unaffected modules may continue operating according to the agent's architecture and authority.

Therefore:

```text
heavy agent workload
        !=
agent shutdown required
```

Instead:

```text
affected module
    |
new calls gated
    |
existing calls drain
    |
replacement performed

unaffected agent operation
    |
continues
```

This is the operational reason for combining filesystem monitoring with deterministic quiescence and the ABI 1.4 replacement lifecycle.

---

## 18. Versioned Deployment Artifacts

A running Windows process may have the canonical module DLL mapped.

An update therefore uses a side-by-side versioned candidate rather than requiring an operator to overwrite the active mapped artifact.

The architectural convention is:

```text
<agent-specific-module-name>.<version>.dll
```

The exact artifact prefix remains agent-specific.

For the Digit reference implementation:

```text
digit_context_recognition.0.1.1.dll
```

The versioned candidate is detected and preflighted. After the active revision reaches the replacement boundary and its DLL is unloaded, the approved candidate can be installed as the runtime artifact.

The common requirement is the versioned candidate behavior, not the literal `digit_` prefix.

---

## 19. Hotload Fail-Closed Behavior

Hotload must preserve the same deterministic trust boundary as startup loading.

A candidate must not become ACTIVE when a required stage fails.

Examples include:

```text
file incomplete or unstable
        -> wait / reject

configuration or identity invalid
        -> reject

required ABI export missing
        -> reject

candidate load failure
        -> reject

ABI incompatibility
        -> reject

verification failure
        -> reject

qualification failure
        -> reject

negative validation failure
        -> reject

activation authorization failure
        -> do not activate
```

For an existing module, candidate preflight failure leaves the current ACTIVE revision undisturbed.

Hotload is not permission to lower qualification standards.

## 20. Hotload Audit and Reporting

Live module changes are operationally significant and must be observable.

The agent should report sufficient lifecycle information to establish:

- module identity;
- previous version where applicable;
- candidate version;
- candidate detection;
- preflight result;
- quiescence;
- stop/unregister result;
- unload result;
- replacement installation;
- verification;
- qualification;
- negative validation;
- activation;
- final disposition.

Persistent audit should record the resulting module transition according to the agent's existing audit architecture.

Hotload must not become an invisible background mutation.

## 24. Migration and Hotload Guidance for Other Agents

Agents adopting ABI 1.4 should:

- use the established STN-LABZ ABI headers and descriptor contract;
- expose `stnlabz_module_get_descriptor`;
- keep lifecycle authority in the owning Core;
- keep agent-specific and module-specific capability outside the common ABI;
- remove duplicated agent-specific lifecycle machinery where the common ABI owns that behavior;
- rebuild and rerun qualification after migration;
- preserve mandatory negative validation;
- verify runtime activation rather than relying on compilation;
- monitor the agent's module directory when live module deployment is required;
- treat newly arrived artifacts as candidates rather than trusted modules;
- preflight replacement candidates before disturbing an ACTIVE revision;
- prevent new calls into a module while replacement is pending;
- allow existing calls to drain before unload;
- use ABI 1.4 stop/unregister lifecycle transitions;
- qualify the replacement revision independently;
- keep the agent running when only a module replacement boundary is required;
- report and audit live lifecycle changes.

Agents should not:

- create another agent-specific copy of the common module ABI;
- embed Core registry machinery inside module DLLs;
- migrate unrelated service APIs merely because the lifecycle ABI changed;
- bypass qualification because a previous revision qualified;
- treat successful compilation as successful migration;
- silently accept missing ABI exports;
- invent compatibility behavior for incompatible modules;
- unload a DLL while code from it is still executing;
- allow filesystem presence alone to authorize activation;
- require an operator reload command for ordinary watcher-triggered hotload;
- shut down an entire agent merely to replace an otherwise isolated module when the architecture supports safe quiescence.

## 25. Failure Interpretation

### `LOADER_EXPORT_MISSING`

The DLL was found and processing reached ABI export validation, but the required descriptor export was absent.

This can indicate an older or incompatible lifecycle interface.

### Linker failures against `stnlabz_module_registry_*`

Core-side ABI implementation has likely been compiled into a module project without its owning registry implementation.

Do not resolve this by recursively copying Core ABI sources into the module.

Restore the Core/module boundary.

### Candidate preflight failure

The proposed replacement did not establish the evidence required to disturb the current ACTIVE revision.

Reject the candidate and preserve the active module.

### Module does not become quiescent

The replacement must not unload code still in use.

Continue according to the agent's approved operational handling rather than forcing an unsafe unload.

### Replacement fails after the active revision is stopped

This is a lifecycle failure requiring explicit reporting and deterministic recovery handling. It must not be hidden by declaring the candidate ACTIVE without successful completion of the required lifecycle.

## 27. Result

STN-LABZ ABI 1.4 establishes a common module lifecycle architecture suitable for STN-LABZ autonomous agents while preserving agent-specific Core authority and module-specific capability.

The resulting relationship is:

```text
                    STN-LABZ ABI 1.4
                           |
                   common lifecycle
                           |
              +------------+------------+
              |                         |
          Agent Core                 Modules
              |                         |
     authority + host-side        consume contract
       integration                     |
              |                  retain capability
              |
     +--------+---------+
     |                  |
module watcher     safe-use control
     |                  |
     +--------+---------+
              |
      live module changes
              |
      ABI-controlled lifecycle
```

Hotload extends that architecture without creating a second lifecycle authority.

The Agent Core observes deployment changes and establishes a safe runtime boundary. ABI 1.4 governs the module lifecycle. The module remains responsible for its capability and qualification behavior.
