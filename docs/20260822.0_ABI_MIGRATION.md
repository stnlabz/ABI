---

## 1. Purpose

This report documents the migration of Digit and its current modules from Digit-specific module lifecycle interfaces to the common STN-LABZ ABI 1.4.

The migration establishes the STN-LABZ ABI as the common module lifecycle boundary used by Digit Core and Digit modules.

The migration was intentionally limited to the module ABI boundary.

Application-specific module functionality remains owned by the individual modules and was not converted into generic ABI functionality.

---

## 2. Migration Objective

The migration objective was to replace Digit-specific module lifecycle contracts with the established STN-LABZ ABI 1.4 contract while preserving existing Digit behavior.

The intended architecture is:

```text
Digit Core
    │
    ├── STN-LABZ ABI 1.4
    │       │
    │       ├── discovery
    │       ├── verification
    │       ├── qualification
    │       ├── activation authorization
    │       ├── activation
    │       ├── stop
    │       └── unregister
    │
    └── Digit-specific Core behavior

Modules
    │
    ├── consume STN-LABZ ABI module contract
    │
    └── retain module-specific service APIs
```

The ABI defines the lifecycle relationship.

It does not replace the internal or application-specific functionality of a module.

---

## 3. Migration Principle

The migration followed the STN-LABZ engineering principle:

> Stay small, deterministic, and easy to operate.

The migration therefore did not attempt to redesign working modules.

Existing module functionality was preserved wherever it was outside the lifecycle ABI boundary.

The migration changed the contract between Core and modules rather than rewriting the modules themselves.

---

## 4. Previous Architecture

Before the migration, Digit used Digit-specific module lifecycle names and interfaces.

Examples included:

```text
digit_module_result_t
digit_module_host_t
digit_module_descriptor_t
digit_module_qualification_result_t
digit_module_get_descriptor
DIGIT_MODULE_API_MAJOR
DIGIT_MODULE_API_MINOR
```

These interfaces performed functions that were no longer specific to Digit.

Maintaining a Digit-specific implementation would duplicate functionality now provided by the common STN-LABZ ABI.

---

## 5. Current Architecture

Digit now uses the STN-LABZ ABI 1.4 module contract.

Equivalent lifecycle interfaces include:

```text
stnlabz_module_result_t
stnlabz_module_host_t
stnlabz_module_descriptor_t
stnlabz_module_qualification_result_t
stnlabz_module_get_descriptor
STNLABZ_MODULE_API_MAJOR
STNLABZ_MODULE_API_MINOR
```

The standard module descriptor export is:

```c
__declspec(dllexport)
const stnlabz_module_descriptor_t *
stnlabz_module_get_descriptor(void);
```

Digit's module loader now expects this ABI-defined export.

A module that does not expose the required ABI entry point is rejected.

---

## 6. ABI Ownership Boundary

A critical distinction established during migration is the difference between an **ABI consumer** and the **ABI host implementation**.

Digit Core owns and executes the ABI lifecycle machinery.

Digit modules consume the ABI contract.

Therefore:

```text
Digit Core
    └── ABI lifecycle implementation

Module DLL
    ├── includes the ABI module contract
    ├── provides its descriptor
    ├── provides lifecycle callbacks
    └── exports stnlabz_module_get_descriptor()
```

A module DLL does not independently embed the Core-side ABI registry implementation.

This distinction was demonstrated during migration when `abi.c` was temporarily compiled into the SQLite module.

The resulting linker errors included unresolved references to:

```text
stnlabz_module_registry_init
stnlabz_module_registry_discover
stnlabz_module_registry_verify
stnlabz_module_registry_qualify
stnlabz_module_registry_authorize_activation
stnlabz_module_registry_activate
stnlabz_module_registry_stop
stnlabz_module_registry_unregister
stnlabz_module_registry_fail
stnlabz_module_registry_find
stnlabz_module_state_string
stnlabz_module_result_string
```

The correct resolution was not to copy additional ABI implementation into the module.

The correct resolution was to remove the Core-side `abi.c` implementation from the module DLL project.

### Rule

**Modules consume the ABI contract. Core owns the ABI lifecycle implementation.**

---

## 7. Module-Specific APIs Remain Module-Specific

The migration does not require every exported module function to become an STN-LABZ ABI function.

For example, the SQLite module retains Digit-specific knowledge retrieval functionality.

Likewise, the context-recognition module retains its own recognition service interface.

These interfaces provide application functionality rather than generic module lifecycle functionality.

The boundary is:

```text
STN-LABZ ABI
    │
    └── module lifecycle

Module-specific API
    │
    └── module capability
```

The two must not be confused.

A service function such as a knowledge query or context-recognition operation does not become part of the common ABI merely because the DLL itself uses the ABI lifecycle.

Observed failure:


After the modules were migrated, both DLLs loaded successfully.

This demonstrates that loader rejection was fail-closed rather than silently accepting an incompatible module contract.

## 14. Important Lessons for Other Agents

Agents migrating to the STN-LABZ ABI should preserve the distinction between generic lifecycle functionality and agent-specific capability.

### Do

- use the established STN-LABZ ABI headers;
- use the ABI-defined descriptor types;
- expose `stnlabz_module_get_descriptor`;
- keep lifecycle authority in the owning Core;
- preserve existing module-specific service interfaces where appropriate;
- rebuild and rerun qualification after migration;
- perform negative validation;
- verify runtime activation rather than relying only on compilation;
- report the ABI version at startup where operationally useful.

### Do Not

- create another agent-specific copy of the common module ABI;
- embed Core registry machinery inside module DLLs;
- migrate unrelated service APIs merely because the lifecycle ABI changed;
- bypass qualification because the previous module revision qualified;
- treat successful compilation as successful migration;
- silently accept missing ABI exports;
- invent compatibility behavior for incompatible modules.

## 15. Migration Failure Interpretation

The migration demonstrated several useful failure distinctions.

### `LOADER_EXPORT_MISSING`

Interpretation:

The DLL was found and load processing reached ABI export validation, but the required ABI descriptor export was absent.

This can indicate that the module still implements an older lifecycle interface.

### Linker failures against `stnlabz_module_registry_*`

Interpretation:

Core-side ABI implementation has likely been incorrectly compiled into a module project without its owning registry implementation.

Do not resolve this by recursively copying Core ABI sources into the module.

Restore the Core/module boundary.

### Compile failure inside the module source

Interpretation:

This is separate from ABI lifecycle runtime validation.

Correct the source/build condition before evaluating loader compatibility.
